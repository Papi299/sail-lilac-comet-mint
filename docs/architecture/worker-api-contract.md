# Worker API Contract

## Internal Worker Control API

The Vercel web runtime orchestrates jobs by communicating with the external worker via a versioned internal REST API.

**Namespace:** `/v1/...`

### Authentication and Replay Prevention

**Mechanism:** HMAC-SHA256 Request Signing.
The browser private-access cookie is NEVER sent to the worker. Vercel and the Worker share a dedicated `WORKER_CONTROL_SECRET`.

**Headers:**
- `x-videofetch-key-id`: Selects the active secret key (for rotation).
- `x-videofetch-timestamp`: Timestamp of the request (Unix epoch seconds).
- `x-videofetch-request-id`: Cryptographically random unique request ID generated by Vercel.
- `Idempotency-Key`: Required for job creation/mutations, generated by Vercel.
- `x-videofetch-signature`: The HMAC-SHA256 signature (hex-encoded).

**Canonical Signing Input:**
The HMAC must be calculated using exact newline-delimited canonicalization:
```text
v1
<KEY_ID>
<METHOD_UPPERCASE>
<CANONICAL_PATH>
<TIMESTAMP>
<REQUEST_ID>
<IDEMPOTENCY_KEY_OR_EMPTY>
<SHA256_RAW_BODY>
```
- Authenticated worker API routes accept NO query parameters. Any unexpected query string is rejected before dispatch. Thus, `<CANONICAL_PATH>` is the exact route pathname (e.g., `/v1/jobs`).
- The body hash MUST be calculated over the exact raw HTTP body bytes, not a parsed or re-serialized JSON object.

**Validation & Replay Prevention (Worker-side):**
The worker must process requests in this exact order:
1. Enforce a hard maximum raw request-body size while reading.
2. Validate header syntax and timestamp tolerance (e.g., within 5 minutes).
3. Calculate and constant-time verify the HMAC (`crypto.timingSafeEqual`).
4. Only AFTER valid authentication, atomically reserve the `x-videofetch-request-id` in the durable replay store.
5. Reject the request if the request ID was already consumed.
6. Only then parse the JSON body and dispatch the operation.

**Replay Store:**
Since SQLite is the worker's durable store, define a small durable replay table:
- `request_id` (UNIQUE)
- `expires_at`
Records are retained slightly longer than the accepted timestamp window and periodically deleted. This prevents an otherwise valid request from becoming replayable if the worker restarts during the timestamp window.
**Note:** Request ID is for anti-replay. It is distinct from the Idempotency Key (which protects business operations from duplication).

**Secret Rotation:**
Secrets are rotated using key IDs:
- `WORKER_CONTROL_KEY_ID=current-2026-...`
- Vercel signs using the current key.
- The worker temporarily accepts both the current and previous key IDs during rotation.
- The previous key is removed after an overlap period greater than the timestamp tolerance.
Unknown key IDs result in an immediate authentication failure. Internal authentication failures must not leak HMAC or security details to the browser.

## Worker DTOs (Data Transfer Objects)

The worker API MUST NOT expose the internal `JobRecord` directly. The data is explicitly split into:

**1. `WorkerJobInternal` (Never leaves the worker)**
Contains sensitive local state:
- `workDir`
- `outputPath`
- command line invocations
- environment values
- local process PIDs

**2. `WorkerJobView` (Returned by the Worker API)**
Safe for transmission to Vercel. When ready, it contains:
- `jobId`
- `status`
- `progress`
- `stageLabel`
- `downloadedBytes`
- `totalBytes`
- `speed`
- `eta`
- `errorCode` (Standard AppError code)
- `safeErrorMessage` (Sanitized)
- `filename` (Display metadata)
- `fileSize`
- `mime`
- `quality`
- `container`
- `createdAt`
- `updatedAt`
- `expiresAt`
- `objectKey` (SERVER-TO-SERVER CONTROL METADATA ONLY)

**Important:** `objectKey` travels from the Worker to the authenticated Vercel control plane, but it MUST NOT appear in the browser-facing/public VideoFetch job DTO. Vercel strictly strips `objectKey` before returning the public response to the browser.

## Job-Create Idempotency

Job creation is rigorously protected by the `Idempotency-Key` HTTP request header, which is generated by Vercel and included in the HMAC signing input. The browser does NOT choose or send this directly.

The worker persists:
- The Idempotency Key (UNIQUE)
- A hash/fingerprint of the normalized creation payload
- The resulting `jobId`
- `expires_at` (tombstone)

**Retention:**
The idempotency record is retained for at least 24 hours, and NEVER shorter than the referenced job metadata lifetime. Even if job metadata is cleaned up early, a tombstone remains to avoid silently recreating the operation. After the idempotency record itself expires, reuse may create a new job.

**Behavior during retention window:**
- New key + valid payload → Creates one job, returns 201 Created.
- Same key + same semantic payload + existing job → Returns the existing job, returns 200 OK.
- Same key + DIFFERENT semantic payload → Rejects conflict (409). Does NOT silently return an unrelated job.
- Same key + same semantic payload + referenced job expired → Returns `EXPIRED` (410). DO NOT create a replacement job.

## Endpoints

### 1. Allocate Job
**POST /v1/jobs**
Idempotently creates a new job.
- **Request Headers:**
  - `Idempotency-Key`: `uuid-v4`
- **Request Body:**
  ```json
  {
    "url": "https://example.com/video",
    "formatId": "best",
    "principalId": "private-access-user"
  }
  ```
  *(Note: `principalId` is the server-defined private-access principal, not browser-selected).*

### 2. Analyze URL
**POST /v1/analyze**
Synchronously analyzes a URL to extract metadata. Worker independently revalidates the URL.

### 3. Get Job Status
**GET /v1/jobs/:jobId**
Retrieves the `WorkerJobView`.

### 4. Cancel Job
**POST /v1/jobs/:jobId/cancel**
Idempotently transitions a queued or running job to the `cancelled` state.

### 5. Diagnostics
**GET /v1/healthz** (Unauthenticated) - Minimal HTTP 200 OK.
**GET /v1/diagnostics** (Authenticated) - Queue depth, active job counts, safe-egress attestations.

## Error Contract

The worker error envelope transports an allowlisted existing VideoFetch `ErrorCode` where applicable. Existing semantic distinctions MUST be preserved across the worker boundary.

**Allowlisted Codes include (but are not limited to):**
`INVALID_URL`, `UNSUPPORTED_SITE`, `VIDEO_UNAVAILABLE`, `ANALYSIS_FAILED`, `FORMAT_UNAVAILABLE`, `PROCESSING_FAILED`, `TIMEOUT`, `NETWORK_ERROR`, `EXTRACTION_FAILED`, `EXTRACTOR_UNAVAILABLE`, `TOO_LARGE`, `TOO_LONG`, `NOT_FOUND`, `EXPIRED`.

**Validation:**
Vercel validates the returned code against the shared allowlist before mapping it into `AppError`.
- Unknown/untrusted worker error code → Maps to a safe fallback like `PROCESSING_FAILED`.
- The worker MUST NEVER expose raw worker exception text, stack traces, or internal HMAC/replay failure details to the browser.

| Worker Scenario | HTTP Status | Allowlisted Code |
| :--- | :--- | :--- |
| Worker unreachable (Network Error) | N/A (Vercel catches) | `WORKER_UNAVAILABLE` (PLANNED NEW Code) |
| Invalid Auth / Replay | 401 Unauthorized | `WORKER_UNAVAILABLE` (DO NOT leak auth detail) |
| Job Not Found | 404 Not Found | `NOT_FOUND` |
| Invalid URL (yt-dlp fails) | 400 Bad Request | `INVALID_URL` |
| Processing Timeout | 408 Request Timeout | `TIMEOUT` |
| Processing Failed | 500 Internal Error | `PROCESSING_FAILED` |
| Job Expired | 410 Gone | `EXPIRED` |
