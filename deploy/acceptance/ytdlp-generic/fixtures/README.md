# The Phase-10D controlled acceptance fixture suite

Four externally reachable fixture families for
`PHASE-10D-YTDLP-PRODUCTION-STAGED-DEPLOYMENT-AND-LIVE-ACCEPTANCE-001`, served
by one small Node service over loopback and exposed for the duration of an
acceptance window by a **separate, temporary Cloudflare Quick Tunnel**.

```
fixture server                    temporary Quick Tunnel
binds 127.0.0.1 only  ─────────►  random *.trycloudflare.com HTTPS origin
(no dependencies, no state on disk, no credential)
```

> **This is test infrastructure.** It is never part of the Production Worker
> service graph, never persistent, never autostarted, and never given a secret.

## Why the fixtures exist

Phase 10D asserts properties of the Worker — the application byte watcher, the
cancellation window, the safe-egress boundary, the direct regression — and every
one of those assertions is only as strong as the source it ran against. A
third-party public video makes the decisive variables somebody else's: its byte
count, its `Content-Length` semantics, its transfer timing, its secondary media
destination and its expected digest can all change between the run that passed
and the review that reads it.

The fixture suite makes those variables **ours** while still crossing the real
public-HTTPS and Worker-egress boundaries during the live run.

```
ephemeral fixture infrastructure  !=  Production infrastructure
```

## The route set

The table is closed. Anything else is `404`; an unsupported method on a known
route is `405`. There is no static-file server, no redirect endpoint, no URL
proxy, no shell surface and no environment dump.

| Route | Methods | Purpose |
| :--- | :--- | :--- |
| `/healthz` | `GET`, `HEAD` | liveness; touches no fixture state |
| `/direct.mp4` | `GET`, `HEAD` | the direct-media control fixture |
| `/generic` | `GET`, `HEAD` | the generic progressive page |
| `/generic-media.mp4` | `GET`, `HEAD` | its deterministically throttled media |
| `/byte-limit` | `GET`, `HEAD` | the unknown-length page (`vf_case` required) |
| `/byte-limit-media.mp4` | `GET`, `HEAD` | the unknown-length media (`vf_case` required) |
| `/byte-evidence` | `GET` only | that one case's own observations |
| `/safe-egress` | `GET`, `HEAD` | the fixed private-v4 destination |

`HEAD` on `/direct.mp4` is a **requirement**, not a convenience: the Worker's
direct analyzer reads `Content-Type` and `Content-Length` from a `HEAD` and
never fetches the body during analyze.

## The media — TWO deterministic MP4s

Both are generated by `prepare-media.mjs` through the **VideoFetch Worker
image's own** `/usr/bin/ffmpeg`, in a container with `--network none`, from
synthetic `lavfi` sources only. No host FFmpeg is required, no third-party
FFmpeg image is pulled, and no external media is involved.

| | direct | generic |
| :--- | :--- | :--- |
| file | `acceptance-fixture.mp4` | `acceptance-generic-fixture.mp4` |
| serves | `/direct.mp4`, and the byte-limit prefix | `/generic-media.mp4` |
| shape | 3 s, 320x240 @ 15 fps | 14 s, 720x576 @ 25 fps |
| bytes | 48,497 | ~10.4 MiB |
| video | H.264 baseline `avc1.42E01E` | H.264 baseline `avc1.42E01E` |
| audio | mono AAC-LC `mp4a.40.2` @ 44.1 kHz | mono AAC-LC `mp4a.40.2` @ 44.1 kHz |

```
node prepare-media.mjs --image videofetch-worker:<tag> --out <dir>
```

It prints both paths, both byte counts and both SHA-256s. Each recipe is
bit-exact (`-fflags/-flags +bitexact`, `-map_metadata -1`), so the same image and
the same recipe reproduce the same bytes and therefore the same digest — which is
what makes "the expected digest was known before the run" checkable by a reviewer
rather than merely asserted. The generic recipe additionally pins `-threads 1`,
because x264's output is a function of its thread count and that is derived from
the host's CPU count; the direct recipe is left exactly as the accepted Stage-A
evidence found it.

**The digests are never derived from what came back through VideoFetch.** Each is
computed from its generated file after FFmpeg exits, and again by the fixture
service at startup from the buffer it will actually serve.

### Why the generic fixture is not the direct one

`PHASE-10D-STAGE-B-SUCCESS-BLOCKER-REMEDIATION-001`. Both routes used to serve
one 48,497-byte body, and `/generic-media.mp4` serves its body throttled across
14 s so the cancellation and shutdown cases have a `downloading` window to
observe.

A 48 KB body spread over 14 s is small enough that the pinned yt-dlp asks for it
in essentially **one** socket read — and that read then spans the whole 14 s,
past the Worker's `--socket-timeout=10`. The first live Stage-B `success`
attempt therefore failed as `TIMEOUT` after three internal download attempts,
with the deployment behaving exactly as configured. Measured boundary, same
48 KB body: 5 s and 8 s throttles succeed, 11 s and 14 s fail.

The Worker's timeout is **not** what changed. The generic fixture is now large
enough that the same 14 s transfer arrives as many completed reads instead of one
long one — which is what a real slow source looks like. It stays bounded
(`GENERIC_FIXTURE_MAX_BYTES`, 32 MiB) because the point is read *shape*, not
bandwidth: the pinned downloader never asks for more than 4 MiB at once, so
~10 MiB over 14 s leaves a wide margin.

## Running it

```
node server.mjs --media <direct mp4> --generic-media <generic mp4> [--port 0]
```

Both are **required**. There is deliberately no fallback from a missing
`--generic-media` to `--media`: silently reinstating the coupling is the one
failure this split exists to prevent, and it would surface live rather than at
startup.

It binds `127.0.0.1` only and prints one JSON manifest line, reporting the two
bodies separately — never one shared digest describing both:

```json
{"listenAddress":"127.0.0.1","listenPort":18080,
 "directPath":"/direct.mp4","directBytes":48497,"directSha256":"…",
 "directMediaPath":"…/acceptance-fixture.mp4",
 "genericPath":"/generic","genericMediaPath":"/generic-media.mp4",
 "genericMediaBytes":10872896,"genericMediaSha256":"…",
 "genericMediaSourcePath":"…/acceptance-generic-fixture.mp4",
 "genericMediaThrottleMs":14000,
 "byteLimitPath":"/byte-limit","byteEvidencePath":"/byte-evidence",
 "safeEgressPath":"/safe-egress","safeEgressExpectedDenyClass":"deny-v4", …}
```

Then expose it, from a config that is **not** the Production one:

```
cloudflared --config /dev/null tunnel --no-autoupdate \
  --url http://127.0.0.1:<port>
```

and build the harness environment from the single temporary origin:

```
VIDEOFETCH_ACCEPT_DIRECT_URL=https://<random>.trycloudflare.com/direct.mp4
VIDEOFETCH_ACCEPT_DIRECT_SHA256=<the manifest's directSha256>
VIDEOFETCH_ACCEPT_GENERIC_URL=https://<random>.trycloudflare.com/generic
VIDEOFETCH_ACCEPT_BYTELIMIT_URL=https://<random>.trycloudflare.com/byte-limit
VIDEOFETCH_ACCEPT_BYTELIMIT_EVIDENCE_URL=https://<random>.trycloudflare.com/byte-evidence
VIDEOFETCH_ACCEPT_EGRESS_REDIRECT_URL=https://<random>.trycloudflare.com/safe-egress
```

The eventual safe-egress case must be invoked with
`--egress-deny-class deny-v4`, because the fixture family is `private-v4` and
`EGRESS_FIXTURE_CLASSES` maps that family to that rule. The class is chosen from
the fixture, **before** the run — never by seeing which counter moved.

### What must never be touched

```
/etc/cloudflared/config.yml      the named Production tunnel
vf-cloudflared                   Production DNS records
Cloudflare Access                Production Vercel routing
```

No persistent Cloudflare configuration is authorized for this suite. If a Quick
Tunnel cannot be created without mutating account or provider state, that is a
blocker to report — not a reason to reconfigure Production.

### Stopping it

Terminate the `cloudflared` process, then the fixture server. Both are ordinary
foreground processes with no unit, no autostart and no on-disk state; stopping
them removes the public exposure completely. The temporary hostname then answers
`530`.

## The four families

### 1. Direct-media control fixture — `/direct.mp4`

Exact bytes, exact `Content-Length`, `video/mp4`, exact SHA-256, known before
any acceptance job. The Worker's direct extractor claims it because the path
carries a media extension, so it exercises the pre-existing direct path.

Its identity — **48,497 bytes**, SHA-256
`44827ff84f50036186a34e7d487ae13afab6934d0b6d17009f5dcf386cd81bdd` — is part of
the accepted Stage-A record `a9ce1c400db8d817` and is served unthrottled, so it
was never affected by the generic route's read-shape problem. It must stay
bit-identical under the authorized Worker image; the recipe is pinned argument
for argument by the test suite.

### 2. Generic progressive fixture — `/generic`

A single-item HTML5 page with exactly one `<video>` carrying exactly one
`<source>`: one progressive `http`/`https` mp4 rendition, no HLS, no DASH, no
fragments, no playlist markup, no authentication and no cookies.

**The media reference is relative**, which is a privacy property rather than a
convenience: the generic success case submits this page URL carrying the
harness's inert sentinel, and a page that reflected the query string (or the
`Host`, or any other request header) into an absolute media URL would carry that
sentinel onward into a media request. Unknown query parameters are ignored and
never rendered.

`/generic-media.mp4` serves the **generic** fixture — never the direct one —
with **deterministic throttling**, a default target of 14 s in 250 ms ticks,
because the cancellation and shutdown cases must observe an owned yt-dlp process
while it is still `downloading`. Throttling changes timing only: every byte is
sent, in order, unmodified, and a completed transfer hashes to the same digest as
the file on disk. **No sleep is added to production code** to create the window.

The throttle spreads whatever body it is given across the same 14 s, so the
body's SIZE is what decides whether the peer sees one long read or many short
ones. That is why this route has its own larger fixture — see
[Why the generic fixture is not the direct one](#why-the-generic-fixture-is-not-the-direct-one).

### 3. Unknown-length byte-limit fixture — `/byte-limit`

Proves the **application byte watcher**, not `--max-filesize`.

The submitted URL carries the harness's 128-bit correlation id, and the page
resolves to `/byte-limit-media.mp4?vf_case=<the same id>`. The grammar is
`^[0-9a-f]{32}$` — byte-identical to `CASE_ID_PATTERN` in
`../lib/evidence.mjs`, asserted equal by the test suite — and matching is exact:
no trimming, no case folding, no coercion, no second query parameter, and a
repeated `vf_case` is refused as ambiguous rather than resolved to the first.

The media response carries **no `Content-Length`**, so Node frames it `chunked`
and the length is genuinely unknown to the client. That is the whole point: the
pinned `HttpFD.real_download` consults `--max-filesize` only inside
`if data_len is not None`, so a declared length would let yt-dlp's own option
stop the transfer and the case would be evidence for the wrong gate.

The stream's ceiling is **528 MiB** against a deployed `MAX_FILE_SIZE` whose
default is 500 MiB. It is a ceiling, not an allocation: the body is the real MP4
followed by one reused 64 KiB block written with backpressure, so the whole
stream costs kilobytes of memory. The expected outcome is that the Worker closes
the connection well before the ceiling.

### 4. Safe-egress fixture — `/safe-egress`

A generic single-item page whose media destination is fixed **in source** at
`http://10.255.255.1/videofetch-denied.mp4` — a literal RFC1918 address, never a
hostname (a name would make the destination depend on what the designated
resolver answered at run time). No query parameter, header, environment variable
or CLI flag can move it; changing it requires changing the constant and getting
that reviewed.

The page itself is public HTTPS through the Quick Tunnel, and its path carries
no media extension, so analysis reaches the generic path rather than the direct
one — which is what makes the case evidence about *generic* egress at all.

**This suite does not prove the firewall denial.** The `deny-v4` counter before,
the request, and the counter after belong to the later live Phase-10D
`safe-egress` case against Production.

## The evidence endpoint

`GET /byte-evidence?vf_case=<id>` — read-only, GET-only, one exact case per
request:

```json
{
  "caseId": "<the id this run minted>",
  "actualMediaRequestObserved": true,
  "mediaRequestCount": 1,
  "contentLengthPresent": false,
  "transferMode": "chunked",
  "bytesServed": 553648128,
  "observedAt": "<iso timestamp>"
}
```

An unknown case is `404`, never a default. There is no `/all`, `/debug`,
`/state` or `/requests`, and the response carries no URL, no request header, no
client address and no user agent — only measurements the fixture made about its
own streaming path.

Nothing is seeded when a page is fetched. A record exists **only** because a
media `GET` for that exact id actually arrived, and:

- a `HEAD` on the media route never opens a case, never increments
  `mediaRequestCount` and never adds to `bytesServed`;
- a page fetch, a health check, a favicon probe and an evidence call all count
  for nothing;
- `bytesServed` accumulates in the `res.write` **flush callback**, so it
  describes bytes handed to the socket rather than bytes queued;
- a second `GET` for the same id is reported honestly as
  `mediaRequestCount: 2`. The harness refuses that (two transfers cannot be told
  apart), which is the correct outcome. **The count is never clamped.**

## Observed pinned-yt-dlp behavior

Measured against `/usr/bin/python3 /usr/local/lib/videofetch/yt-dlp`
(**2026.08.19**) from a retained VideoFetch Worker image, in a disposable
container with `--network none` running both the fixture and yt-dlp over
loopback.

### HTTP requests (§11 — Range)

| Phase | Requests |
| :--- | :--- |
| analysis (`-J --skip-download`) on a page | one `GET` of the page; **no media request** |
| download on the same page URL | one `GET` of the page, then **exactly one** `GET` of the media |

**No `Range` header was issued on any route**, in either phase; every request
was a plain `GET` with `Accept-Encoding: identity`, and no `HEAD` came from
yt-dlp at all. A partial-content path would therefore be unused complexity, so
the fixture declares `Accept-Ranges: none` and answers the whole object whatever
the client asks for — one response shape, deterministic.

The one-media-request property depends on submitting the **page**. Handing
yt-dlp the media URL directly produces **two** GETs, because the Generic
extractor fetches the URL itself to decide whether it is HTML before the
downloader fetches it again. Acceptance submits pages, so this does not arise —
and if it ever did, the fixture would report `2` rather than hide it.

### Extraction results

| Fixture | `_type` | extractor | live | renditions | selected media |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `/generic` | `video` | `HTML5MediaEmbed` | absent | 1 | `…/generic-media.mp4` |
| `/byte-limit?vf_case=<id>` | `video` | `HTML5MediaEmbed` | absent | 1 | `…/byte-limit-media.mp4?vf_case=<the same id>` |
| `/safe-egress` | `video` | `HTML5MediaEmbed` | absent | 1 | `http://10.255.255.1/videofetch-denied.mp4` |

Every one is a single non-live item with `_type: "video"`, no `entries`, one
`http`/`https` progressive mp4 rendition, and no HLS, DASH or fragment
reference. The Worker's `extractor` field is application-owned (`"yt-dlp"`) and
is not read from upstream, so `HTML5MediaEmbed` satisfies
`requireGenericStrategy`.

A full download through the page URL wrote `source.mp4` whose SHA-256 equals the
generated fixture's exactly, confirming the throttle is a scheduler and not a
transformer. A download of the byte-limit media with `--max-filesize` set far
below the transfer **did not stop it** — confirming, against the pinned binary,
that the fixture genuinely defeats `--max-filesize` and leaves the application
byte watcher as the only gate.

### Worker contract mismatch found during this verification — CORRECTED IN SOURCE

The pinned extractor's output **could not produce a generic video preset** in the
Worker as merged, for two independent reasons. This was a defect in
`src/worker/analysis/ytdlp-analysis.server.ts`, not in the fixture, and it
blocked the live generic, byte-limit and safe-egress cases — all three call
`pickPreset` and fail without one.

> **Status.** Discovered here, during fixture provisioning, and corrected in
> source by `PHASE-10D-GENERIC-REAL-OUTPUT-COMPATIBILITY-001`. The defect is
> left recorded as it was found rather than edited away, because it is why this
> suite merged ahead of the live phase. **Live Phase 10D has still not been
> executed** — Stage A, enabling generic, and Stage B all remain outstanding,
> and nothing here claims Production acceptance.

**D1 — `hasAudio` is unreachable for any video-bearing format.**
`selectCandidates` requires `audio_ext !== "none"`, but `_fill_sorting_fields` in
yt-dlp 2026.08.19 sets `audio_ext` to `"none"` on **every** format whose
`vcodec !== "none"`:

```python
if format.get('vcodec') == 'none':
    format['audio_ext'] = format['ext'] if format.get('acodec') != 'none' else 'none'
    format['video_ext'] = 'none'
else:
    format['video_ext'] = format['ext']
    format['audio_ext'] = 'none'
```

`audio_ext` is a **sorting field**, not a statement that a format has no audio.
So `hasVideo && hasAudio` — which `buildGenericPresets` requires for every video
preset — is structurally impossible for real output, for any source, not only
this fixture. The repository's unit tests pass because their fixture omits
`audio_ext` entirely, so `undefined !== "none"` holds.

**D2 — the HTML5 path never reports a `vcodec`.** `_parse_html5_media_entries`
parses the `<source type="...; codecs=...">` declaration into `vcodec`/`acodec`
and then overwrites it:

```python
formats = [{'url': full_url, 'vcodec': 'none' if cur_media_type == 'audio' else None, 'ext': ext}]
...
f.update(formats[0])          # clobbers the parsed vcodec with None
```

so `vcodec` comes back `null` and `hasVideo` is false as well. `acodec` survives
(`mp4a.40.2`), which is why the fixture still declares the true codec pair.

Reproduced **as the defect stood** against the real captured documents, by
calling the Worker's own `selectCandidates` and `buildGenericPresets`:

| format shape | candidates | presets |
| :--- | :--- | :--- |
| repository test fixture (no `*_ext` keys) | `hasVideo`, `hasAudio` | `preset:best`, `preset:1080`, … |
| real muxed video (`vcodec` + `acodec` + `audio_ext: "none"`) | `hasVideo` only | **none** |
| real HTML5 (`vcodec: null`) | **none** | **none** |
| real audio-only (`vcodec: "none"`) | `hasAudio` only | `preset:audio`, `preset:mp3` |

Neither the fixture nor the acceptance harness could be changed to paper over
this: doing so would have meant fabricating codec metadata, and the
evidence-schema contract is deliberately not ours to weaken. The Worker was
fixed instead.

#### What the correction changed

Audio presence is now decided by `acodec` alone — `audio_ext` keeps no presence
authority in either direction. Video presence distinguishes three codec states,
the governing rule being that **unknown is not absent**: only the exact marker
`"none"` proves a stream is missing, while `null` merely means the codec
identity was not reported. An unknown `vcodec` can establish video only from
coherent shape evidence (`video_ext` a real container, equal to `ext`, and in
the generic VIDEO allowlist), and no codec, height, fps or size is ever
invented — `videoCodec` stays `null` for this fixture.

Acquisition was corrected with analysis, because the strict `[vcodec!="none"]`
filter would otherwise have rejected the very format analysis had just approved:
`_build_format_filter` never passes a `None` field to its operator. The private
selection now records HOW video was established, and the selector's video half
follows it:

| how video was established | selector |
| :--- | :--- |
| a reported codec | `[vcodec!="none"]` |
| coherent `video_ext` (this fixture) | `[vcodec!=?"none"][video_ext="mp4"]` |
| proven absent | `[vcodec="none"]` |

Re-verified end to end against this suite with the pinned binary: `/generic`
reaches `preset:best`, the selector re-selects format `0`, and the acquired file
is byte-identical to the served fixture with no merge and no FFmpeg.
`verify-selector.py` covers the same expectations against the real runtime
inside the image.

## Tests

`scripts/ytdlp-fixture.test.mjs` runs entirely over loopback and needs no
Internet, no Docker, no VM and no Cloudflare. Media generation itself is proven
against the pinned image in the acceptance run rather than in this suite, which
asserts the recipes and the route-to-body mapping instead. It covers the loopback bind, the
closed route and method sets, path traversal, exact direct bytes/length/digest,
the single relative generic reference, sentinel non-reflection, exact generic
media bytes, a real throttle delay within bounds, the exact `vf_case` grammar
and its refusals, absent `Content-Length`, genuine and unclamped media-request
counts, `HEAD` counting for nothing, per-case isolation, genuine byte counts
including an early peer close, the evidence route's exact key set and absence of
client metadata, the fixed and immovable safe-egress destination, and the
manifest's freedom from secrets.
