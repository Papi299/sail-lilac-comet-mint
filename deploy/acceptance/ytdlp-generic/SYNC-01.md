# SYNC-01 — the split-merge timing matrix release child

**Test tooling only.** Nothing here runs during Worker startup, and none of it
ships in the Worker image. SYNC-01 runs **only** as a child of the SPLIT-07
release-image gate (`split07-release-image-candidate-07` and later), inside the
exact candidate image, offline. It never deploys anything.

SYNC-01 answers the question `SPLIT-MERGE-TIMESTAMP-PRESERVATION-AUDIT-001`
raised:

> Does the split merge in the image a deployment would run keep the source's
> relative audio/video timing, for every container shape a split pair can
> arrive in, rather than re-basing each input to zero on its own?

SPLIT-06 (`-05`) and DASH-01 (`-02`) answer it on their full paths, for three
shapes. SYNC-01 drives the candidate's own `mergeSplitMedia` directly across a
deterministic matrix of nineteen, including the shapes no full-path fixture
carries: shared non-zero bases, absolute `tfdt`, edit-list pre-roll, Vorbis,
and pairs whose earlier-starting half is the shorter one.

```
for each of 19 cases (generated in the candidate by its own /usr/bin/ffmpeg):
  video-only half + audio-only half, one presentation timeline, one sync event
  → harness ffprobe packet timelines of both halves      (the pre-job oracle)
  → harness decode of the flash and the click             (the pre-job event offset)
  → expected closed policy from the measured start order  (+ Opus CodecDelay)
  → the candidate's mergeSplitMedia, its FFmpeg spawn observed
  → harness ffprobe packet timeline + decode of the merged artifact
  → zero-aligned controls only: the historical 73176b20 merge, compared
+ oracle sensitivity: the historical merge of two offset cases must be DETECTED
  → SYNC-01 PASS (sync01-release-image-merge-timing-01)
```

---

## The matrix (`fixtures/sync-media.mjs`)

Every case is a video-only half (`testsrc2` 320×180, 30 fps) and an audio-only
half (48 kHz mono: a 220 Hz bed with a 20 ms 1 kHz burst), authored on **one**
presentation timeline. A full-white frame and the burst both sit at
presentation time 2.000 s. Each half's container timestamps place its first
media unit at `base + start`. Every time is an integer number of milliseconds,
and every video time is a multiple of 100 ms, so each frame boundary is exact.

| Case | Kind | Shape |
| :--- | :--- | :--- |
| `mp4-prog-zero` | control | progressive MP4, zero-aligned; AAC priming hidden by the audio edit list |
| `mp4-prog-zero-bframes` | control | as above with B-frames: negative video DTS under an edit list |
| `mp4-prog-audio-late` | offset | audio starts 478 ms later (empty edit ~456 ms) |
| `mp4-prog-video-late` | offset | video starts 400 ms later |
| `mp4-prog-shared-base` | offset | both on a 10 s base: video +100 ms, audio +578 ms |
| `mp4-prog-audio-leads` | offset | 10 s base, audio +100 ms, video +500 ms, B-frames |
| `mp4-frag-dashlike-bframes` | offset | fragmented, the muxer's own zeroing, B-frame composition delay, no edit list |
| `mp4-frag-tfdt-audio-late` | offset | fragmented, **absolute `tfdt`** (`+frag_discont`), audio +478 ms |
| `mp4-frag-tfdt-shared-base` | offset | fragmented, absolute `tfdt`, 10 s base, B-frames |
| `mp4-prog-preroll-cut` | control | 0.5 s of video pre-roll hidden by its edit list |
| `mp4-prog-audio-leads-short` | duration | video +400 ms; the audio, which starts first, ends at 3 s |
| `mp4-prog-video-leads-short` | duration | audio +478 ms; the video, which starts first, ends at 3 s |
| `webm-opus-zero` | control | zero-aligned; Opus `CodecDelay` makes the demuxed audio start at −7 ms |
| `webm-opus-audio-late` | offset | audio +478 ms |
| `webm-opus-video-late` | offset | video +400 ms |
| `webm-opus-shared-base` | offset | 10 s base, video +100 ms, audio +578 ms |
| `webm-opus-audio-leads` | offset | 10 s base, audio +100 ms, video +500 ms |
| `webm-vorbis-zero` | control | zero-aligned Vorbis (no `CodecDelay`) |
| `webm-vorbis-audio-late` | offset | Vorbis, audio +478 ms |

- **control:** zero-aligned on disk. The corrected merge must produce exactly
  what the historical merge produced (bytes for MP4, the packet timeline for
  WebM) and must move nothing.
- **offset:** a legitimate relative offset the merge must preserve.
- **duration:** an offset case whose **earlier-starting** half is the
  **shorter** one, so a direction chosen from duration instead of start time
  trims media.

## What one PASS proves

For every case, against an oracle the harness fixed **before** the merge:

| Check (per case) | Meaning |
| :--- | :--- |
| `fixture/halves-generated` | both halves were generated by the candidate's FFmpeg |
| `fixture/source-timing-established-before-the-merge` | both halves' packet timelines were measured before the merge |
| `fixture/decoded-sync-event-measured-in-both-halves` | the flash and the click were decoded from the halves |
| `fixture/pair-carries-a-discriminating-av-offset` | (offset, duration) the source offset exceeds the rounding tolerance |
| `fixture/earlier-starting-half-is-the-shorter` | (duration) the case discriminates start order from duration |
| `merge/product-merge-returned-the-merged-artifact` | `mergeSplitMedia` returned the expected output path |
| `merge/one-ffmpeg-merge-with-the-pre-job-sync-policy` | exactly one FFmpeg run, whose input options are exactly the expected closed policy, with no forbidden timestamp flag |
| `sync/payload-identical` | every packet's payload is the source's |
| `sync/codec-parameters-preserved` | codec and extradata unchanged |
| `sync/relative-offset-preserved` | audio-minus-video first-presented offset, and the per-stream shift delta, within the tolerance |
| `sync/each-stream-shifted-by-one-constant` | every packet of a stream moved by the same amount |
| `sync/no-media-hidden-or-unhidden` | the same packets, and the same discard flags |
| `sync/no-leading-gap` | the earliest presented media starts no later than one tolerance after zero |
| `sync/stream-spans-preserved` | each stream's presented span is unchanged |
| `sync/decoded-sync-event-preserved` | the decoded click-minus-flash offset is the source's, within the tolerance |
| `compat/output-identical-to-the-historical-merge` | (control) identical to the historical merge's output |

Plus the release identity (exactly HLS-09's), five toolchain preflights, and
`oracle/detects-per-input-zeroing/<case>` for `mp4-prog-audio-late` and
`webm-opus-audio-late`: the historical merge of each must be reported as **not**
preserving timing. 281 mandatory checks in all.

**The expected policy** is derived by the harness, independently of the
Product, from its own packet measurement: MP4 syncs to whichever half is first
presented first (the video on a tie), so `-isync 0` before input 1 or
`-isync 1` before input 0. WebM syncs the audio to the video, preceded for Opus
by `-itsoffset` of the track's own `CodecDelay` (read from the fixture's bytes,
quantized through the 48 kHz Opus clock, printed with six decimals).

**The tolerance** is one tick of the output video time base plus one tick of the
output audio time base plus (MP4) one tick of the movie timescale, to which the
mov muxer rounds each track's start delay down. Typical values: MP4 1,086 µs,
WebM 2,000 µs. The decoded-event check uses the same tolerance.

**Packet identity, not time, aligns the timelines.** Output packets are matched
to source packets by payload SHA-256, so a dropped or added packet shows up as a
payload or discard-count failure, not as a time offset.

## What one PASS does NOT prove (`SYNC01_NON_CLAIMS`)

- No acquisition. The halves are generated locally and handed to the merge
  primitive directly. SPLIT-06 and DASH-01 carry the full path.
- No real public source, site or CDN. The prevalence of offset pairs in the
  wild is not measured.
- No MPD `presentationTimeOffset`. The pinned yt-dlp does not carry it, so a
  source whose AdaptationSets differ only by PTO is outside this claim.
- No player-specific rendering claim. Synchronization is measured with the
  pinned FFmpeg's own demuxer and decoder.
- No Production startup of the candidate, no promotion, and no long-term uptime
  claim.

## The evidence

**Schema: `sync01-release-image-merge-timing-01`** (`lib/sync-evidence.mjs`).

- **Identity** is the release identity the SPLIT-07 parent observed: source
  commit and tree (clean), candidate build label, immutable image id, the run
  subject Docker executed, and loopback-only interfaces.
- **A PASS requires every one of `SYNC01_MANDATORY_CHECKS` present exactly once
  and passing.** The builder refuses otherwise, and the parent's validator
  (`validateSyncChildRecord`) refuses independently.
- **Privacy.** The record is an allowlist. No key named `argv`, `stderr` or any
  credential may appear, and no string anywhere may contain `/tmp/videofetch`,
  the harness scratch path, `http://` or `https://`. Any `-itsoffset` value
  outside the application's exact six-decimal form is recorded as `<other>`,
  never verbatim.
- The parent re-reads the exact bytes, validates them, hashes them, and
  re-hashes them before assembling its own record (`syncAcceptance`).

## Running it

Only through SPLIT-07 (see `SPLIT-07.md`). The driver launches it with
`releaseSyncAcceptanceRunArgs`: the DASH-01 release posture (`--network none`,
`--read-only`, `--cap-drop=ALL`, `no-new-privileges`, the Product media workspace
bound at `/tmp/videofetch`, the harness scratch tmpfs) with **no** `--add-host`.
It re-derives that posture structurally before launch
(`releaseSyncRunPostureViolations`). Each case merges inside
`/tmp/videofetch/sync01/<case>`, which is removed after the case. The whole
matrix takes about half a minute.

A standalone run (for diagnosis only; it produces no release record) takes the
same identity flags as DASH-01:

```sh
node --import ./scripts/register-ts-aliases.mjs --experimental-strip-types \
  deploy/acceptance/ytdlp-generic/sync-matrix.mjs \
  --evidence /report/<name>.json --source-commit <40-hex> --source-tree <40-hex> \
  --source-context-clean --candidate-tag videofetch-worker:split07-<sha12>-local-test \
  --candidate-image-id sha256:<64-hex> --run-image-id sha256:<64-hex>
```
